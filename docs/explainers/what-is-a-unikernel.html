What is a unikernel, and what is Hermit?

Start with a question that sounds silly: what is the operating system actually for? Not what it does — what problem does it solve that you would otherwise have to solve yourself? Once that has a sharp answer, unikernels stop being exotic. They are what you get when the answer turns out to be "nothing, in this particular case."

The OS is a referee

Your program does not touch the network card. It cannot. It asks the kernel to, through a system call — and that call is not an ordinary function call. It flips the CPU from unprivileged mode into privileged mode, crosses into a different address space, does the work, and flips back.

Why that ceremony? Because a normal computer runs many mutually-untrusting programs on one piece of hardware. Your browser must not read your password manager's memory. Two programs both wanting the network must not corrupt each other's packets. The kernel is the referee: it isolates, it multiplexes, it enforces. The privilege boundary is what gives the referee teeth — programs cannot cheat, not merely should not.

That is a genuinely hard problem and the kernel solves it well. But notice the premise it rests on: many mutually-untrusting programs, one machine.

Now break the premise

Picture a Firecracker microVM whose entire job is to run one Minecraft server. One program. No users logging in, no cron, no second tenant. The VM itself is already isolated from every other VM by the hypervisor.

Who is the referee protecting whom from? There is only one player.

So all that machinery becomes pure cost. A scheduler juggling processes that do not exist. Drivers for hardware that is not there. A privilege boundary defending your program from itself. A unikernel is the observation that in this situation you can delete the referee: link the kernel and the application into a single program, in one address space, at one privilege level.

A system call becomes a function call. Not a faster system call — an ordinary call instruction into code that happens to live in the same binary.

The same line of Rust, two different worlds

Here is what makes Hermit specifically interesting rather than just academically cute. Write this:

let listener = TcpListener::bind("0.0.0.0:25565")?;

You do not change that line. You change the compilation target. Watch what the same source does in each world.

The point is not that one is faster. It is that the boundary moved. On Linux, std is a library that calls the kernel. On Hermit, std is the interface to a kernel that is part of your binary. Same API, radically different thing underneath — which is exactly why your code compiles unchanged, and also why the failure modes are strange. More on that below.

Why virtio keeps coming up

A unikernel still runs on a hypervisor, so its "hardware" is emulated. Emulating a real network card faithfully — register by register, interrupt by interrupt — is slow and pointless, because the guest knows perfectly well it is virtualised.

virtio drops the pretence. Guest and host agree on a shared-memory ring buffer: the guest writes packet descriptors into a queue, rings a doorbell, the host picks them up. No device emulation, just a queue. That is why a unikernel needs a virtio driver and roughly nothing else — virtio-net for networking, and the driver is a few thousand lines rather than the tens of thousands a real NIC would take.

This is where a request for "virtio-mem" runs aground. virtio-mem is hot-plug memory — growing a guest's RAM at runtime. In Rust guest-land it does not exist: Hermit's driver set is console, fs, net and vsock, and the virtio-drivers crate has no driver, no issue and no PR for it. Only a Linux guest under Firecracker 1.14+ has it today.

What you give up, concretely

Delete the referee and you delete the things the referee provided. Some of that you will not miss. Some of it half your dependency tree assumes exists.

C librariesmostly breakthey assume POSIX, which assumes a kernel to call

That last row is the one that decides everything in practice. When this was tried on hyperion, 11 of 24 crates cross-compiled — and pure-Rust ones sailed through, including the protocol layer and an entire ECS. The blockers were four C-shaped dependencies: socket2 ("doesn't support the compile target"), openssl-sys, libz-ng-sys, ring. Everything downstream of those fell over with them.

A bug that only this architecture can have

This one is worth sitting with, because it teaches the model better than any diagram.

The build produced an image that booted, printed to the console, and then failed every single socket call with an uninformative Kind(Uncategorized). Same source, same kernel, different Rust nightly: works first try.

Why? Because std is compiled against a specific version of the Hermit kernel interface. The old nightly's std spoke hermit-abi 0.4; the kernel answered 0.5. Networking had moved.

Now ask why this cannot happen on Linux in the same way. Because the Linux syscall ABI is frozen essentially forever — a binary from 2005 still runs. That stability is a deliberate, expensive promise, and you only notice it exists when you step somewhere it is not being made. On a unikernel the "syscall ABI" is a Rust crate version, and crate versions move.

So when is this actually worth it?

Boot time is the honest headline. In the real run, the guest was listening 13.166 ms after boot and answered a client in 3.6 ms. There is no init, no udev, no systemd, no userspace at all — the binary is the machine. If you are spinning up a VM per request or per match, that number is the whole argument.

The attack surface argument is real but narrower than it is usually sold: a smaller kernel means fewer bugs, but "no privilege separation inside the VM" means a bug that does exist has nothing standing in its way.

And the cost is the table above. A Minecraft server that wants TLS, compression and a memory-mapped world database is asking for exactly the C libraries that do not survive the trip. Which is why the sober conclusion from the experiment was: the proxy is a plausible target, the full game server is not, yet.

Check yourself

1. Why does a unikernel make a "system call" cheaper?

There is no ring 3 to ring 0 transition, because there is only one ring. The kernel is linked into your binary, so the "call" is a call instruction. Note this also means a bug in your code can scribble on kernel memory — you traded safety for speed, deliberately.

2. Pure-Rust crates cross-compiled fine; ring and openssl-sys did not. What is the actual dividing line?

All three blockers ship C. C libraries are written against POSIX — file descriptors, mmap, syscalls — and Hermit provides only part of that. Rust code targeting std just needs std to exist, which is precisely what Hermit supplies.

3. "Bare metal" here means the code runs with no hypervisor at all. True?

Bare metal here means no OS between your code and the machine it sees. That machine is still virtual: QEMU, Firecracker or uhyve, with virtio devices. Hermit can boot on real hardware, but the whole toolchain and every driver is aimed at the virtualised case.
